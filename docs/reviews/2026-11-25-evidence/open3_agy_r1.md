## R4-A3
- Choice: A
- Why: All three heterodyne joint paths share the same bug: `_build_joint_problem`/`_build_joint_result` (`xpcsjax/optimization/nlsq/heterodyne_core.py:3340-3346,3826-3853`), `_fit_joint_averaged_multi_phi` (`xpcsjax/optimization/nlsq/heterodyne_core.py:1411-1417,1665-1697`), and `_fit_joint_constant_multi_phi` (`xpcsjax/optimization/nlsq/heterodyne_constant_mode.py:202-208,366-404`) already materialize a concrete `(n_phi, N, N)` `weights_batch` before building the closure, yet pass `data_only_residual.size` (or `final_residual.size`) for DOF and reduced chi-squared (and constant mode calls no covariance DOF rescaler at all). Computing the contributing-row count at problem-build time by applying the kernel's own `_offdiag_indices` (`xpcsjax/core/heterodyne_jax_backend.py:311,471-472`) to `weights_batch > 0` matches homodyne's `_n_contributing_rows` precedent (`xpcsjax/optimization/nlsq/strategies/stratified_ls.py:165-183`), cannot miscount exact-zero residuals (eliminating B), and is bit-identical on unweighted/all-positive-weight fits (standing rule 1). Using that single count for covariance DOF, `diagnostics["covariance_dof"]["n_valid"]`, and `noise_normalized_reduced_chi2` keeps all reported statistics internally consistent.
- Risks / conditions: `_drop_penalty_rows_from_dof` (`xpcsjax/optimization/nlsq/heterodyne_core.py:1926-1948`) MUST be generalized before wiring: today it short-circuits on `if not n_penalty_rows:` (line 1941) and scales by `(dof_valid + n_penalty_rows) / dof_valid` (line 1946), which silently skips zero-weight correction whenever `n_penalty_rows == 0` (including constant mode and `regularization_mode="none"`) and under-corrects when `n_penalty_rows > 0`. Replace the formula with `n_rows_solver` (total residual rows seen by the solver = `n_data_rows_total + n_penalty_rows`): no-op only when `n_rows_solver == n_valid`, return all-NaN covariance/uncertainties when `n_valid - n_params <= 0` (which automatically sets `covariance_is_placeholder=True` at `heterodyne_core.py:1798,3987` and `heterodyne_constant_mode.py:461`), and otherwise rescale by `(n_rows_solver - n_params) / (n_valid - n_params)`. Verify in unit tests: (1) unweighted fits are bit-identical, (2) masked 2D and 3D weights rescale covariance/uncertainties and reduced chi-squared across individual, averaged, and constant modes both with and without L3 penalty rows, and (3) masking down to `n_valid <= n_params` yields all-NaN covariance/uncertainties and `covariance_is_placeholder=True`.
## data-B9
- Choice: B
- Why: `xpcsjax/data/xpcs_loader.py:820` has always read `cache_file_path` (defaulting to `data_folder_path`) and ignored `cache_directory`, so all existing user caches live beside the data. Beyond avoiding orphaned caches and new write-permission failures, honouring `./cache` (Options A/D) is actively hazardous: `cache_filename_template` (`xpcsjax/config/templates/xpcsjax_laminar_flow.yaml:106`, `"cached_c2_frames_${start_frame}_${end_frame}.npz"`) omits the dataset filename, so routing programmatic/dict configs (which bypass `ConfigManager._resolve_data_paths` at `xpcsjax/config/manager.py:394`) or multi-dataset configs into a shared `./cache` causes cross-dataset cache collisions and `CacheStaleError` thrashing. Option C is also broken by design because `_resolve_data_paths` (`xpcsjax/config/manager.py:369,420-422`) expands `"./cache"` into an absolute path before the loader ever sees it. Removing `cache_directory` from the four templates and `ConfigManager` defaults and documenting `cache_file_path` keeps behaviour unchanged and aligns docs with reality.
- Risks / conditions: Two implementation pitfalls must be handled: (1) `xpcsjax/data/xpcs_loader.py:820` uses `self.exp_config.get("cache_file_path", data_folder)` — if the templates document `cache_file_path: null` (matching `file_path: null` at `xpcsjax_laminar_flow.yaml:94`), `.get()` returns `None` and `os.path.join(None, cache_filename)` at `xpcs_loader.py:845` raises `TypeError`; change line 820 to `self.exp_config.get("cache_file_path") or data_folder` (and document clearly that `cache_file_path` is a directory path despite its name). (2) To honour standing rule 2 for users with older configs that customized `cache_directory`, emit a deprecation `WARNING` in `xpcs_loader.py` when `cache_directory` is present in `exp_config` and `cache_file_path` is unset/empty, remove `"cache_directory"` from `ConfigManager._DATA_PATH_KEYS` (`manager.py:369`) and `_get_default_config` (`manager.py:452`), and test `cache_file_path: null`, explicit `cache_file_path`, and the `cache_directory` warning.
## core-B3

- Why: On the opt-in `NLSQAdapter` path (`xpcsjax/optimization/nlsq/adapter.py:620,1032`), failing loudly with a clear `ValueError` when the data's time range exceeds the fallback grid `[0, 10000 * dt]` eliminates silent clamping (`xpcsjax/core/jax_backend.py:377-390,539-554`) immediately with zero changes to `get_or_create_model` (`adapter.py:358`) or `ModelCacheKey` (`adapter.py:115`). - Risks / conditions: Hoist `_FALLBACK_GRID_SIZE = 10001` (currently duplicated locally at `xpcsjax/core/jax_backend.py:377,539`) to a module-level constant in `jax_backend.py` and import it in `adapter.py` so the guard cannot drift. Guard both `t1` and `t2` for `t_max > (_FALLBACK_GRID_SIZE - 1) * dt * (1.0 + 1e-12)` (a small relative tolerance prevents false failures at exact `10000 * dt`) and `t_min < -1e-12 * dt` in `_build_model_function` (covering both `enable_cache=True` and `enable_cache=False`, homodyne modes only — skip `two_component`, which passes `t` directly to `compute_c2_heterodyne`), and apply the same concrete-array check on `_xdata_cache` miss in `get_or_create_model`'s `model_func` (`adapter.py:595-614`, gated on `isinstance(xdata, np.ndarray)`) so direct callers cannot silently clip either. Test: `t_max == 10000 * dt` succeeds, `t_max > 10000 * dt` raises `ValueError` mentioning the default path on both cached and uncached adapter modes, and `t_min < 0` raises `ValueError`.
